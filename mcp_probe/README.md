# lxm-mcp-probe — 선행 시험 서버

Jdot HQ(ChatGPT)가 OAuth로 붙인 원격 MCP 도구를 **사람 없이, 예약으로** 부를 수 있는지를
짓기 전에 재는 서버다. 드롭·버킷·원장 어느 것에도 닿지 않는다. 가진 것이 없다.

배경: `hub-ops/from-organum/173` §1, `hub-ops/from-lxm/151` §4·`152`, `hub-ops/from-organum/174`(둘이 맞춘 계획).

## 묻는 것

| # | 물음 | 어떻게 보나 |
|---|---|---|
| 0 | JJ의 계정에서 사용자 연결 기능이 켜지는가 | 커넥터를 만들 수 있는가 |
| 1 | 대화에서 한 번 승인한 뒤에 다시 묻는가 | `probe_read`를 같은 대화에서 두 번, 새 대화에서 한 번 부른다 |
| 2 | 예약 실행에서 사람 없이 불리는가 | 예약 시각의 서버 기록에 `tools/call`이 있는가 |
| 3 | 도구 응답을 얼마나 기다리는가 | `probe_wait`를 30, 50, 70, 90, 120초로 부른다. 기록의 `caller-gone`이 답이다 |
| 4 | 잠든 서버를 기다려 주는가 | 20분 넘게 아무도 건드리지 않은 뒤에 부른다 |
| 5 | 사람 없이 토큰을 갱신하는가 | 접근 토큰이 10분이다. 뒤의 호출에서 `refresh_generation`이 오르는가 |
| 6 | 도구의 응답은 얼마나 커도 되는가 | `probe_read`에 `pad_bytes`를 1024, 16384, 65536, 262144로 준다 |
| 7 | 응답의 글자가 모델에 그대로 닿는가 | 응답마다 64자 `nonce`가 실린다. Jdot이 본 값을 적고 서버 기록과 맞댄다 |
| + | 읽기 전용 표시가 승인의 동작을 바꾸는가 | 표시 없는 `probe_read_unmarked`를 불러 1과 견준다 |

어느 것도 되는 것으로 전제하지 않는다.

## 띄우기 (JJ)

Render 대시보드 → New → Web Service → 이 저장소, `main`.

| 칸 | 값 |
|---|---|
| Name | `lxm-mcp-probe` |
| Runtime | Python 3 |
| Build Command | `pip install -r mcp_probe/requirements.txt` |
| Start Command | `uvicorn mcp_probe.app:app --factory --host 0.0.0.0 --port $PORT` |
| Instance Type | Free |
| Auto-Deploy | Off |

환경 변수는 하나다.

| 이름 | 값 |
|---|---|
| `PROBE_PASSCODE` | Generate로 만든 값. **복사해 둔다** — 연결을 승인하는 화면에서 한 번 넣는다 |

- 값이 없거나 16자보다 짧으면 서버가 뜨지 않는다.
- 이 값을 바꾸면 이미 내준 토큰이 모두 무효가 된다. 철회가 필요하면 값을 바꾸고 다시 띄운다.
- 고칠 수 있는 것(보통은 그대로 둔다): `PROBE_ACCESS_TTL`(초, 기본 600), `PROBE_REFRESH_TTL`(기본 30일),
  `PROBE_REDIRECT_PREFIXES`(기본은 OpenAI 문서의 두 콜백).

뜬 뒤 확인: `https://<이름>.onrender.com/`이 JSON으로 답한다. MCP 주소는 `https://<이름>.onrender.com/mcp`다.

## 붙이기와 시험 (Jdot · JJ)

1. ChatGPT에서 커넥터를 새로 만든다. 주소는 위의 `/mcp`, 인증은 OAuth.
2. 승인 화면이 뜨면 `PROBE_PASSCODE`를 넣는다.
3. 대화에서 `probe_read`를 두 번 부른다. 둘째에 승인을 다시 묻는지 적는다. 새 대화에서 한 번 더 부른다. (물음 1)
   - 부를 때마다 답의 `nonce` 64자를 화면에 보이는 대로 적는다. (물음 7)
   - `probe_read_unmarked`도 한 번 부른다. 묻는 모양이 `probe_read`와 다른지 적는다.
4. `probe_wait`를 30, 50, 70, 90, 120초로 차례로 부른다. 어디서 실패하는지 적는다. (물음 3)
   - `probe_read`에 `pad_bytes`를 1024, 16384, 65536, 262144로 준다. 답의 `filler`가 `filler_ends_with`의 값으로
     끝나는지 묻는다. 끝나지 않으면 잘린 것이다. (물음 6)
5. 예약을 둘 건다. 둘 다 `probe_read`를 부르고 답을 그대로 적게 한다.
   - **깨어 있는 서버**: 예약 시각 5분 전에 `/`를 한 번 열어 둔다. (물음 2)
   - **잠든 서버**: 예약 시각 앞 20분 동안 아무도 건드리지 않는다. (물음 4)
6. 예약의 답에서 `refresh_generation`과 `token_age_s`를 본다. (물음 5)

**잠든 서버 시험 중에는 `/`를 열지 않는다.** 여는 것 자체가 서버를 깨우고 15분을 다시 센다.

## 답 읽기

도구의 답에 실리는 것:

| 칸 | 뜻 |
|---|---|
| `server_utc` | 서버의 시각 |
| `tool_calls_since_boot` | 이 인스턴스가 깬 뒤 몇 번째 호출인가. 1이면 잠들었다 깬 것이다 |
| `uptime_s` | 깬 지 몇 초인가 |
| `token_age_s` | 이 접근 토큰이 나온 지 몇 초인가 |
| `grant_age_s` | 승인한 지 몇 초인가 |
| `refresh_generation` | 토큰을 몇 번 갱신했는가. 0이면 승인 때의 토큰 그대로다 |
| `waited_s` | `probe_wait`가 기다린 초 |
| `nonce` | 이 응답에만 있는 64자. 서버 기록의 같은 줄에도 남는다 |
| `filler_bytes` · `filler_ends_with` · `filler` | `pad_bytes`를 준 때의 채움. 끝의 표지가 채움보다 앞에 적혀 있어 잘리면 드러난다 |

서버 기록은 Render 대시보드의 Logs에 한 줄에 JSON 하나로 남는다. `"probe"`로 찾는다.

| `probe` | 언제 |
|---|---|
| `boot` | 인스턴스가 떴다. 요청이 깨웠다는 뜻이다. 그 뒤에 `rpc` 줄이 없으면 부른 쪽이 기다리지 않은 것이다 |
| `mcp` (`auth`) | 토큰 없이, 또는 만료된 토큰으로 불렀다(401) |
| `register` · `authorize` · `approve` · `token` | 연결과 갱신의 걸음 |
| `rpc` | MCP 요청 하나. `header_protocol`이 플랫폼이 말하는 규격의 판이다 |
| `wait` | `begin`, `end`, 그리고 **`caller-gone`**: 부른 쪽이 `gone_after_s`초에 끊었다. 1초 단위로 올림한 값이다 |

우리가 쓰는 줄에는 요청 본문도 토큰도 암호도 남지 않는다.

## 모양

- 요청 하나에 JSON 응답 하나. 세션도 스트림도 없다. `/mcp`의 GET은 405다. 본 창구(Organum 173 §3)와 같다.
- 말하는 규격은 `2025-11-25`까지의 handshake 판이다. `2026-07-28`의 `server/discover`에는 「모르는 메서드」로 답하고,
  공식 SDK 클라이언트는 그 답을 받고 `initialize`로 물러난다(SDK 2.3.0으로 확인).
  - 그 답은 **HTTP 200**에 JSON-RPC 오류 -32601을 실은 것이다. ChatGPT가 물러나지 않으면 이것부터 본다(Organum 174 §1).
  - 첫 요청의 메서드와 `header_protocol`이 「플랫폼이 어느 판을 말하는가」의 답이다. 본 창구의 판은 그것으로 정한다.
- 디스크에도 메모리에도 기억하는 것이 없다. 코드와 토큰은 `PROBE_PASSCODE`로 봉한 값이라, 인스턴스가 잠들었다
  깨어도 앞서 내준 것이 그대로 통한다. 대가로 코드와 갱신 토큰의 한 번-쓰기는 한 부팅 안에서만 지켜진다.
- 승인 화면의 암호 하나가 인증의 전부다. 본 창구의 신원 제공자가 아니다.

## 둘째 판 — 나갈 창구를 다시 붙인다 (0.3.0)

첫 판의 결과는 `hub-ops/from-lxm/156`에 있다. ChatGPT는 두 시대를 말하고, 한 번 부르는 데 120초를 주며,
예약 셋이 사람 없이 잠든 서버에서도 왔다. 둘째 판은 **나갈 코드**를 붙여 본다(Organum 176 §3, 181).

같은 서비스가 organum 0.9.0 후보(dev pin `9043877`, 판정 `hub-ops/from-lxm/160`)의
`hub_front.MailFront`를 같은 승인 뒤에 싣는다. 시험은 그 후보 묶음으로 돌았다. 0.9.0이 나온 뒤 저장소의 묶음은
공개 cut(`vendor/organum-323419a.tar.gz`)이다. 코드는 같고 판 번호 한 줄만 다르다. 읽는 길은 꾸며 낸 편지 셋(`sample_reader`)이다.
여전히 드롭·버킷·원장에 닿지 않는다.

| 주소 | 무엇 |
|---|---|
| `/mcp` | 첫 판의 `probe_*` 도구. 그대로다 |
| `/mail` | 우편 창구. 호출자에게 우편함이 있다. 편지 셋 가운데 001과 003이 그 앞이다 |
| `/mail-nobox` | 같은 창구인데 호출자에게 우편함이 없다. 어떤 호출이든 403이다 |

**띄우기 (JJ).** 설정은 그대로다. Render에서 Manual Deploy로 최신 커밋을 올린다. 빌드가 후보 묶음을 깐다.
`/`가 `"version": "0.3.0"`으로 답하면 올라간 것이다.

- `PROBE_MAIL_MODERN=0`을 넣으면 창구가 `2025-11-25`까지만 말한다. 첫 판의 서버와 같은 모양이다.
  새 판(`2026-07-28`)으로 붙지 않을 때 값만 바꿔 다시 띄운다.

**붙이기와 볼 것 (Jdot · JJ).** `/mail`로 커넥터를 하나 더 만든다. 승인 화면의 암호는 같다.

| # | 볼 것 | 어떻게 |
|---|---|---|
| 1 | 새 판으로 오는가 | 서버 기록의 `mail` 줄. `header_protocol`이 `2026-07-28`이고 `initialize`가 없으면 새 판이다 |
| 2 | 한 번의 호출이 요청 넷에서 셋으로 주는가 | 같은 줄을 센다 |
| 3 | 엄격한 머리가 오는가 | `header_mcp_method`, `header_mcp_name`, `meta_keys` |
| 4 | 받는 이로 추려지는가 | `mail_list`가 001과 003만 낸다. `examined`는 3이다 |
| 5 | 남의 편지와 없는 편지가 같은 답인가 | `mail_get`으로 002와 099를 청한다 |
| 6 | 우편함이 없는 호출자 | `/mail-nobox`로 커넥터를 만들어 본다. 붙지 않아야 한다(403) |
| 7 | 예약이 커서를 넘기는가 | 예약을 두 번 건다. 둘째 회의 `mail` 줄에서 `arg_names`에 `cursor`가 있는가 |
| 8 | 맞지 않을 때 | `PROBE_MAIL_MODERN=0`으로 내려 다시 붙는가 |

**기록.** 창구의 줄은 둘이다. 어느 줄에도 값은 없다. 커서도, 편지의 글도 적지 않는다.

| `probe` | 실리는 것 |
|---|---|
| `mail` | 메서드, 상태 코드, 판의 머리, `Mcp-Method`의 값과 `Mcp-Name`이 있는지, `_meta`의 이름들, 도구와 인자의 이름들 |
| `mail-audit` | 창구의 감사 고리가 넘긴 기록. 호출자, 도구, 연 봉투의 문과 번호, 내준 편지의 문과 번호, 시각 |

uvicorn의 접근 기록은 서버가 뜰 때 끈다. 첫 판의 기록에 승인 요청의 질의 문자열이 찍혔기 때문이다.

## 셋째 판 — 발신의 앞 시험 (0.4.0)

읽기에서는 도구의 **답**이 얼마나 커도 되는지와 그 글이 모델에 그대로 닿는지를 쟀다. 발신은 화살표가 거꾸로다.
모델이 편지의 본문을 도구의 **인자**로 넘기고, 서명될 것은 도구가 받은 바이트다. JJ가 2026-10-10에 Jdot HQ의 발신을
커스텀 플러그인의 꼴로 설계하자고 했고(`hub-ops/from-lxm/180`), 그 꼴이 되는지를 짓기 전에 잰다. 꾸민 글만 쓴다.

| # | 물음 | 어떻게 보나 |
|---|---|---|
| 8 | 도구의 인자는 얼마나 커도 되는가 | `probe_text`로 1000, 4096, 16384, 65536, 262144바이트의 글을 받아 `probe_receive`에 넘긴다 |
| 9 | 모델이 받은 글이 도구에 글자 그대로 닿는가 | `probe_receive`가 `matches_reference`와 처음 달라진 자리를 답한다 |
| + | 읽기 전용이 아닌 도구를 부르기 전에 플랫폼이 묻는가 | `probe_receive`는 읽기 전용 표시가 없다. 대화에서 한 번, 예약에서 한 번 부른다 |

- `probe_text`가 주는 글은 편지를 닮았다. 한글, 표, 백틱, 곧은 따옴표, 낫표, 줄표, 64자 지문, 빈 줄, 끝의 줄바꿈이 들어 있다.
  조사가 어색한 문장도 있다(「승인는」). 고쳐 적으면 달라진 것으로 잡힌다.
- 서버는 준 글을 기억하지 않는다. `reference`의 이름에서 같은 글을 다시 만든다.
- `probe_receive`는 아무것도 보관하지 않고 보내지 않는다.
- 서버 기록(`"probe": "rpc"`)에는 받은 크기, 지문의 앞 16자, 맞았는지, 요청의 크기가 남는다. 글은 남지 않는다.

적어 줄 것: 호출마다 시작과 끝의 시각, 넘긴 크기, 답의 `received_bytes`·`matches_reference`·`first_difference_at`,
그리고 **화면이 부르기 전에 무엇을 물었는지**. 실패했으면 오류의 글 그대로.
